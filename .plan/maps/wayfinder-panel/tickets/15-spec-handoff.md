# Spec handoff

## Question

How is the finished `spec.md` cut into an implementation map that build sessions take ticket by ticket? Decide the implementation map's slug and destination, how build tickets are sliced (by layer, by surface, or by vertical slice through server, contracts, and client), their order and blocking edges, which ticket carries the chartr port and its tests, where PR boundaries fall given "one request is one PR", and what each build ticket's Done-when must include (tests per `AGENTS.md`, before/after captures for UI, the flat-trace).

## Done when

The answer names the implementation map, lists its tickets with type, blockers, and Done-when, and states how `spec.md` sections map onto them, so the finale can write `spec.md` and chart that map without further decisions.

## Answer

Decided on 2026-11-04 by a subagent standing in for the user, at the user's request, after a self-run grilling round.

**Implementation map.** Slug `wayfinder-panel-impl`, at `.plan/maps/wayfinder-panel-impl/`. Ticket 10's picker sorts it next to `wayfinder-panel`, so the two read as a pair without any `-impl` marking.

Destination: "The Wayfinder tab ships in web and desktop as `../wayfinder-panel/spec.md` describes, and agents reach start and release through MCP. Six stacked PRs, one per ticket, are merged to `main`, each with green CI, its tests, and its captures. Nothing in the spec is left unbuilt or changed without a new ticket on the `wayfinder-panel` map."

Notes for the map:

- `../wayfinder-panel/spec.md` is the source of truth. A build session loads this map, its one ticket, and the spec sections the ticket names. It does not reread the `wayfinder-panel` tickets unless the spec cites one for a detail.
- Domain and vocabulary are the `wayfinder-panel` map's Notes, plus **session state** from ticket 14 (Working, Needs you, Unattended, derived by `claimSessionState` in `packages/shared` on client and server, never stored). Read `AGENTS.md` first. Server tickets read `docs/internals/effect-services.md` before touching `apps/server`.
- Build sessions do not call `grilling` or `domain-modeling`; the decisions are made. If the spec is silent or wrong on something the build needs, stop, open a ticket on the `wayfinder-panel` map, and wait. Do not decide it in the PR.
- Skills by ticket. Every ticket calls `tdd` for the logic it lists under tests. UI tickets (02, 03, 04, 05) also call `apple` and `impeccable`, and the session runs `test-t3-app` once after integrating, using the `Replay (dev)` provider wherever a turn is needed. Ticket 06 reads `evals/README.md` and runs the evals it names. No ticket uses `diagnose` unless a failure needs runtime instrumentation.
- Branches and PRs. One ticket is one request and one PR. `AGENTS.md` asks for a maintainer's request before splitting, and a subagent standing in for the user cannot give it. So the first build session asks the maintainer to confirm the split before opening PR 01. If they decline, the same six tickets land in order as commits on one branch and one PR, and every Done-when still applies per ticket. Each ticket branches from the previous ticket's branch (`wayfinder/01-snapshot-service`, and so on), and its PR targets that branch until the one below merges, then is retargeted to `main`. PRs merge in ticket order. Conventional titles; body ends with the model and harness. Captures go to GitHub, never into the repo.
- Every Done-when includes `vp run check:changed` passing, a written "Hit every surface" walk in the PR body naming which entries applied, and a docs check against the `AGENTS.md` documentation rules.
- The flat-trace is manual and required for any ticket that changes `apps/web/src/components/wayfinder/starmap/` or the host's calls into it (02, 03, 05). Use an uncommitted local paint counter as the prototype did, or a DevTools performance recording, and paste the paint table (mount, idle 3 s and 5 s, click a star, resize, maximize, plus the ticket's own rows) into the PR. The committed proof is the stop-table test: empty rAF queue and zero timers at rest.

**Slicing.** Vertical where a slice can stand alone, server-first where it cannot. The renderer port cannot ship alone: `check:changed` runs knip, and an unmounted port is dead code. So the port ships with its host tab in ticket 02. The snapshot service ships first, alone, because it has no visible surface and every client slice reads it; it is reachable through its RPCs, so it is not dead code. Start and release go in one slice, server through readout, because a claim write without its reverse would be a one-way door.

**Excluded.** One PR for the whole build: about 5,000 lines across server, contracts, renderer, and UI is too large to review and would hold the snapshot service behind the UI. Layer-by-layer tickets (all contracts, then all server, then all web): each layer would land as dead code until the next, and knip fails on that. Shipping the renderer port as its own PR, for the same reason. A feature flag to hide the tab between merges: 02 and 03 merge back to back instead. A separate docs ticket: docs go with the slice that makes the feature usable. Grilling inside build sessions. A new worktree per build ticket from the panel, since ticket 07's active-checkout rule still holds; build sessions branch by hand.
